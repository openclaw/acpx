# ACP Conformance Profile v1 (Draft)

## Purpose

Define a minimal, stable conformance profile for ACP transport/session behavior
that can be validated across adapters.

This profile intentionally focuses on the highest-leverage interoperability
surface first.

## Normative language

The key words "MUST", "MUST NOT", "SHOULD", and "MAY" are to be interpreted as
RFC 2119 terms.

## Transport assumptions

- Transport is JSON-RPC 2.0 over stdio streams.
- Requests use unique client-generated `id` values.
- Notifications do not include `id`.

## Required methods in profile v1

- `initialize`
- `session/new`
- `session/prompt`
- `session/cancel`

Adapters under test MUST also emit `session/update` notifications during prompt
execution. Completion is reported by the original prompt response; a separate
terminal update is not required.

## Contract requirements

1. `initialize`

- Adapter MUST respond with a valid JSON-RPC success response.
- Response MUST include a protocol version value.
- `agentCapabilities` MAY be omitted. When present, it MUST be a JSON object,
  not an array, null, or primitive value. Object extension members are allowed.

2. `session/new`

- Adapter MUST return a non-empty session identifier.
- If session capabilities are returned, they MUST be an object.

3. `session/prompt`

- Adapter MUST accept a valid content block payload within negotiated
  capabilities. Core cases use baseline `text` and `resource_link` blocks;
  embedded `resource` blocks require advertised `embeddedContext` support.
- Adapter MUST emit at least one `session/update` notification before terminal
  completion for non-empty prompt execution.
- Successful completion MUST be reported by a `stopReason` in the original
  `session/prompt` response.

4. `session/update`

- Update notifications MUST reference an existing session id.
- Ordinary progress updates do not need a synthetic terminal-state variant;
  the prompt response carries the final stop reason.

5. `session/cancel`

- `session/cancel` is a notification without an `id` and MUST NOT receive a
  separate JSON-RPC response.
- A still-active prompt MUST acknowledge cancellation by returning
  `stopReason: cancelled` in its original `session/prompt` response.
- Idle cancellation has no prompt response to await. The idle case sends the
  notification for a valid session and does not assert a remote acknowledgement.

Deterministic active-cancellation and permission scenarios use the bundled mock
profile, whose command semantics make those operations observable. The core
profile does not require arbitrary adapters to interpret mock commands.

6. Error semantics

- Invalid request params MUST yield a JSON-RPC error (typically `-32602`).
- Operations for unknown session ids MUST yield an explicit error (not silent
  success).
- Permission denials triggered by client policy MUST be represented as explicit
  failures with machine-readable code/message.

## Timing guidance

- Each case defines:
  - `request_timeout_ms`
  - `update_timeout_ms`
  - optional `settle_timeout_ms`
- Runner SHOULD treat timeout as a test failure with captured transcript.

## Case file schema (runner-facing)

Each case JSON object includes:

- `id`: stable case id
- `title`: human-readable title
- `profile`: intended scope (`acp-core-v1` or `acpx-mock-v1`); the selected
  profile's required case ids determine execution
- `description`: goal of the case
- `permission_mode` (optional): per-case override (`approve-all` or `deny-all`)
- `steps`: ordered operations consumed by the runner engine
- `checks`: required outcomes evaluated after steps
- `timeouts`: timeout budget per case

The runner's `filesystem_operation` check is a case-wide assertion of completed
local read/write callbacks. It matches the callback's session, literal request
path, write content where applicable, and success or a specific error code.
Successful read assertions may check a case-insensitive substring of the
returned content. Only callbacks completed before check evaluation count. This
does not establish which prompt caused the operation or whether the peer
received its response. The deterministic mock filesystem cases use this check;
it adds no natural-language command requirement to the core adapter profile.

## Pass/fail model

- A case passes only if all assertions pass.
- A profile run passes only if all required cases pass.
- Optional cases MAY be reported separately without failing the profile.

## Out of scope for v1

- `session/fork`
- `session/list`
- `session/resume`
- `session/set_model`
- `$/cancel_request`

These can be introduced in later profile revisions once their semantics are
stable across adapters.
